# v0.3.0 — Verify what you forged

The forge builds the feature. This release adds the two stages that come after it, and formalizes the test discipline that makes the loop fast enough to be worth running.

Existing workspaces: run `/aiforging:update-targets`. Everything here is additive, and nothing under `docs/features/` is touched.

## Two optional stages, after the forge

**`/aiforging:browser-testing`** walks a feature's `testing.md` in a real browser. It marks the checklist items only a person can judge — visual, "reads clearly" — so you work those in parallel, walks the rest, and records one line of plain-text evidence per step.

It never fixes what it finds. A failing step means the product and the specification disagree; it says nothing about which one is wrong, and deciding that requires knowing what the feature is *for*. An auto-fixer there would cement the wrong assumption **and** hand you a green checklist saying so. Findings go to `escalations.md` and to a conversation.

**`/aiforging:review-loop`** runs rounds of review → triage → fix across every repo a feature touched. Reviews fan out in parallel (they're read-only); fixes serialize per repo (a shared test database can't take two). Every finding is verified against the source before it's accepted — in practice about a third describe deliberate behavior. Findings are classified by change class rather than by felt confidence, because a confident agent is exactly the one that doesn't ask.

Run browser-testing first. Review rounds can run to exhaustion on a diff while a behavioral defect sits untouched in the most-used screen, and the cheapest moment to reverse a wrong decision is before ten work items are built on it.

Both are optional. Both are workspace-level. Neither writes a feature.

## One test suite per feature — and nothing runs the whole thing

Every feature registers one named test suite before its first test. Every later work item augments that same suite. Fire agents, Hammer agents, and fix agents run that suite and only that suite.

A three-second loop and a three-minute loop are not the same activity at different speeds. But scoping trades a real risk: a regression in a *different* feature won't show up. So the framework doesn't pretend otherwise — every stage now **stops at the end of implementation and hands you the full suite in words**, with the command, and a reminder that each refactor was an atomic commit and is individually revertible.

That handoff used to be an optional recommendation at the end of a Hammer pass. It's now mandatory and unconditional, because a recommendation after a pass that went well is exactly the note that gets skipped.

Details: `conventions/tdd/feature-test-suite.md`.

## `testing.md`, `overview.md`, `summary.md`

The feature-folder convention now specifies all six document roles.

**`testing.md`** is required for any feature with a UI surface: a QA checklist a person clicks through, covering access and gating, then the happy path, then edge cases. One per feature — never one per work item — ordered by work item in the nested shape. Written *before* implementation ends, because a checklist written afterwards describes what was built, and one written from the spec describes what was supposed to be built. It's also the required input to `browser-testing`, which refuses to run without it rather than inventing one.

`/aiforging:new-feature` now asks whether the feature has a UI surface and scaffolds the skeleton — or records in the spec why it's being skipped, since a missing checklist with no explanation is indistinguishable from an oversight.

**`summary.md`** is an optional post-implementation snapshot for features with three or more work items. **`overview.md`** is the work-item umbrella for the nested shape, now properly specified.

## Additions will actually reach you now

`.claude-plugin/artifacts.json` describes every artifact the plugin copies out of itself — destination, scope, target roles, and update policy. `/aiforging:setup`, `/aiforging:update-targets`, and `/aiforging:uninstall` all read it.

Previously each of those carried its own hardcoded list. Adding an artifact meant editing three files, and forgetting one meant it installed on fresh setups and never propagated to anyone already using the plugin — silently. Manifest entries carry a `since` version, so `update-targets` can tell an update from an addition and present additions as explained offers rather than surprise installs.

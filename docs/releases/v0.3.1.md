# v0.3.1 — what the first real upgrade found

v0.3.0 shipped a manifest-driven upgrade path that had never been executed end to end. It was run the next day against a production monorepo — Symfony backend plus React frontend, onboarded at v0.1.0, carrying ten user-captured patterns and seven locally-customized convention files.

**It passed.** No user-owned file was modified, nothing went missing, and a three-way merge kept a hand-added cross-reference while taking the plugin's change to the same file. Verified against checksums taken beforehand, not against the run's own account of itself.

It also surfaced six defects. This release fixes all of them.

## The two that were real bugs

**The workspace check rejected a real workspace.** It looked for its marker in the first 500 bytes of `CLAUDE.md` — a file the framework encourages you to customize, and which `/aiforging:update-targets` explicitly treats as "commonly customized." Add a paragraph above the marker and a genuine workspace reports as not-a-workspace. Now greps the whole file, everywhere.

**`/aiforging:setup` could destroy your `.gitignore`.** It used `cat >`, which is harmless for a new workspace directory and destructive for a monorepo or single-repo workspace, where the file belongs to your repo and may be hundreds of lines long. Now appends only the rules that are missing, matched whole-line, and never rewrites.

Relatedly: seven backup files landed tracked-eligible because the workspace's rule was `.claude/*.bak-*`, which misses both nested paths and the backups written into `.aiforging/` and `docs/`. The plugin had carried the correct `*.bak-*` rule for releases — but `.gitignore` wasn't in the artifact manifest, so nothing propagated it. **That is exactly the failure mode the manifest exists to prevent, reproduced by the manifest.** It's a manifest entry now, and `update-targets` checks the rules and offers to add what's missing.

## The two design gaps

**Empty pattern tiers cannot survive git.** The run offered to create a tier directory that had never held a tracked file in the repository's entire history — because `mkdir` alone produces a directory git will not store. It vanishes on the next checkout, it's missing for everyone who clones, and the offer recurs on every future run, indefinitely. Both tiers now ship with a `README.md` explaining the two-tier model: git keeps it, the loop ends, and the explanation lands in the directory you're about to write a pattern into.

**Nothing recorded which version your copies came from.** The run reconstructed it — thirteen files showed as modified, most of them customizations of files the release never touched, and separating those took several extra passes. It worked because the run was careful. A less careful one presents all thirteen as needing update, you accept, and your customizations are replaced. `.aiforging/VERSION` now records the release, so the comparison is a fact rather than an inference. Absent, the command falls back to inference, says so out loud, and defaults customized-looking files to skip.

## The two polish items

The upgrade-time offer for new skills read like a changelog entry — it described what they do and never said why you'd want them, while `/aiforging:setup` carried the actual reason. The asymmetry was backwards: at upgrade time you're being interrupted about something you've never heard of, so the explanation has to work *harder* there. And two interim counts were off by one, both inside the sentence describing what was protected from modification — the worst available place to be approximately right.

## Upgrading

```bash
claude plugin marketplace update aiforging
claude plugin update aiforging@aiforging --scope project   # scope from `claude plugin list`
```

then `/aiforging:update-targets` from your workspace. Additive; nothing under `docs/features/` is touched. This run writes your first `.aiforging/VERSION`, offers any missing `.gitignore` rules, and installs the tier placeholders — after which the "create the empty patterns directory?" prompt stops recurring.

## The part worth keeping

The pre-release audit found nine defects and was worth running. Not one of these six was reachable by it — every finding that audit produced was a claim the repo made *about itself*, and every one of these is a claim about the outside world. Two of them had been latent for two releases, reachable only by someone who had actually upgraded, which nobody ever had.

Instructions that have never been executed are not documentation. They are a hypothesis.
